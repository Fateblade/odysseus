## Ollama

Installed version is unknown: do not claim an upgrade delta until inventory. Latest stable v0.40.13 adds LFM3 Linux/Windows support; it is not advertised as a gfx1151 performance release. Newer development [OpenAI sampler fix](https://github.com/ollama/ollama/commit/c1db5f9ef203b2e946161bf4c6bd4f2ec7f123b3) preserves model sampler defaults when the request omits them. It is beyond the observed stable tag, and can change output quality/reproducibility versus older OpenAI-compatible requests; explicit sampler values remain essential in comparisons.

Official [v0.40.13 GPU documentation](https://github.com/ollama/ollama/blob/04088e7c9d41cba5d33bafbf788d87a465c79d5b/docs/gpu.mdx) lists gfx1151 / Ryzen AI Max+395 and requires ROCm v7 on Linux. This is official device support, not qualification of every Ubuntu package/kernel combination. Preserve the working driver/compiler stack and inspect bundled runner libraries separately. No evidence here requires a gfx architecture spoof.

The same version's Vulkan backend is **enabled by default when installed**; older advice to enable an experimental backend is version-specific. `OLLAMA_VULKAN=0` or `GGML_VK_VISIBLE_DEVICES=-1` disables Vulkan, and `GGML_VK_VISIBLE_DEVICES` selects devices. Vulkan memory reporting can be approximate without additional capability/root privileges; verify actual allocations rather than making privilege changes as a performance tweak. Compare ROCm and Vulkan only in separate candidate service runs with logs proving which backend and offload are active. No matched 395 result establishing Vulkan superiority was located.

The [pinned FAQ](https://github.com/ollama/ollama/blob/04088e7c9d41cba5d33bafbf788d87a465c79d5b/docs/faq.mdx#how-can-i-enable-flash-attention) says FA is automatic when backend/device support it; force with `OLLAMA_FLASH_ATTENTION=1`, disable with `=0`. Do not describe FA as universally off by default. Quantized KV requires FA. `OLLAMA_KV_CACHE_TYPE` is global: `f16` default, `q8_0` approximately half KV memory with small precision loss, `q4_0` approximately quarter with potentially greater long-context quality loss. High-GQA models may be more sensitive. These fractions concern KV only, not whole-model memory, and compatibility must be verified per model/backend rather than inferred from device support.

Keep concurrency fixed: current FAQ documents `OLLAMA_NUM_PARALLEL=1` default and memory scaling with parallelism × context. Reducing context or parallelism can restore GPU fit without increasing kernel speed. Quantized KV is a memory/quality tradeoff, not a guaranteed TPS win.

Required future inventory (not executed): `ollama --version`, `/api/version`, service executable/container image digest, startup environment and logs, runner/backend/library identities, kernel/driver, `/api/tags` model digests, `/api/show` architecture/quantization/template/parameters, `ollama ps` or `/api/ps` offload/residency, explicit context/parallel/max-loaded settings, FA/KV type and actual memory. Record native API versus `/v1` sampling/usage behavior and router `keep_alive` unload policy. Stable version benefits can then be selected against the installed baseline.
